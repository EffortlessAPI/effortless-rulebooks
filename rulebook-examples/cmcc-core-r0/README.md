# cmcc-core-r0 — the CMCC-Core theorem, made runnable

This example is the runnable companion to the paper *CMCC-Core Representation
Theorem* (referred to below by section number). It exists to answer four
objections that the rest of this repo does not address:

| Objection | What this example does about it |
|---|---|
| The repo tests output equality, not structural transparency | Adds a second gate, **reflection**, that checks constructor reflection (§13) on the substrate *artifact*, and a matrix where three substrates pass the answer key and only one passes reflection |
| The demo domains are not formally R0 programs | Ships `r0-lint`, which decides membership in R0 (§21's five restrictions) and emits a certificate or a violation list, plus one spec it accepts and one it rejects |
| A rulebook projected into substrates could be an interpreter encoding | Ships that encoding as a substrate (`substrates/interpreter`), shows it passing the answer key, and shows the reflection gate rejecting it on five of six conditions |
| The conformance matrix is self-reported | Expected traces are generated by a reference evaluator and cross-checked state-by-state against an independent evaluator (SQLite's join engine); the matrix is produced only by `conformance/run.py`; the 21-test suite runs the whole pipeline from scratch |

The result, from `conformance/matrix.json`:

```
substrate    answer key  reflection  conformant
transparent  True        True        True
tangled      True        False       False
interpreter  True        False       False
```

All three compute the same answers. Only one of them is a *representation* in
the paper's sense. That divergence is the whole demonstration: the answer key
tests adequacy (§11); it cannot see transparency (§13).

## Run it

Python 3.10+ and `pytest`; no other dependencies for the pipeline itself. This
example is also a full Effortless Rulebook (ERB) project — its own structure
(the R0 spec, the conformance matrix) is additionally modeled as rulebook
data and served through a small app reading Postgres `vw_*` views (see
"As an ERB project" below).

```bash
cd rulebook-examples/cmcc-core-r0
./start.sh                      # rebuild + test + ingest into Postgres + launch the app
```

`./start.sh` does, in order: (1) the original pipeline — `conformance/run.py`
(transpile the substrates, generate expected traces, build the matrix) then
the 21-test `pytest` suite; (2) push the freshly computed
`conformance/matrix.json` into the local database (`conformance/ingest_conformance.py`);
(3) launch the Express + React app on `http://localhost:43106`
(API on `:43306`). Run `./init-db.sh` once first to create the database.

The individual pipeline commands, run by hand:

```bash
python3 conformance/run.py      # transpile, generate expected traces, build the matrix
python3 -m pytest tests -q      # 21 tests, ~1 s
python3 tools/r0_lint.py r0/spec.json        # certificate (exit 0)
python3 tools/r0_lint.py r0/not-r0.json      # VG violations (exit 1)
python3 tools/reflection_check.py r0/spec.json substrates/interpreter/interpreter.py
```

## As an ERB project

Beyond the pipeline above (unchanged from the original research artifact),
this directory follows this repository's canonical Effortless Rulebook (ERB)
project shape: `effortless.json`, the hub at
`effortless-rulebook/effortless-rulebook.json`, `rulebook-to-postgres` +
`rulebook-to-rulespeak`, and a `CLAUDE.md` explaining the project-specific
doctrine (most importantly: the direction-of-truth rule that keeps the
rulebook from ever becoming a fourth, un-independent implementation of R0
semantics — see `CLAUDE.md`).

The rulebook models the spec's own structure (`EDBRelations`, `Commands`,
`Rules`, `Transitions`, `TransitionEffects`, `TransitionEvents`,
`IntegrityConstraints`, `Observables`, `SeedFacts`, `InputHistories`,
`ReflectionConditions`) as a faithful transcription of `r0/spec.json`, and
the conformance matrix (`Substrates`, `AnswerKeyResults`,
`ReflectionResults`) as witnessed data ingested from a fresh
`conformance/matrix.json`. `Substrates.AnswerKeyOk` / `.ReflectionOk` /
`.Conformant` are the one rulebook-native computation: an `AND`/`COUNTIFS`
roll-up over those already-witnessed rows — never a re-derivation of R0's
stratified-Datalog/bitemporal semantics.

```bash
effortless build   # regenerate postgres/ + rulespeak/ from the rulebook
./init-db.sh        # once (or after a schema change): recreate erb_cmcc_core_r0
```

## What is here, and which section of the paper it implements

```

r0/not-r0.json               a spec r0-lint must reject (value generation)   §3, §14
r0/inputs/*.json             input histories i                               §8
r0/expected/*.json           Obs_R0(c, i, h), as trace SETS                  §9
tools/r0lang.py              syntax, tau rules, stratification, G_R          §4, §7, §12
tools/r0_lint.py             membership in R0                                §21
tools/engine.py              chi: transitions, constraints, successor sets   §8, §20
tools/reference_eval.py      derived state by naive stratified fixpoint      §3–6
tools/sqlite_oracle.py       the same rules compiled to SQL (independent)    §11
tools/gen_expected.py        expected traces, reference x oracle             §11
tools/reflection_check.py    the six conditions of constructor reflection    §13
substrates/transparent/      transpiler -> one function per G_R node         §12–13
substrates/tangled/          images exist, dependencies hidden (control 2)   §23
substrates/interpreter/      D = program, F = eval (control 1)               §6, §13
conformance/run.py           the two-gate matrix                             §11, §13, §20
tests/                       the pipeline, end to end
```

### The specification

`r0/spec.json` is small enough to read in one sitting and exercises every
construct the proof depends on at least once:

- positive recursion with no value generation (`Reachable`), so Lemma 1's
  finite lattice applies;
- negation and aggregation over strictly lower strata (`Isolated`, `Fanout`,
  `MaxCap`), so the stratum operator is monotone;
- an empty group, so §5's table is tested (`COUNT` gives 0, `MAX` derives
  nothing);
- an event history with valid and knowledge time, and a correction command,
  so §7's snapshot rules do real work — `i2-bitemporal` observes the same
  shipment at three (valid, known) pairs and gets three different answers;
- integrity constraints that reject a transition (`SelfRoute`, `NegativeCap`);
- one command (`Reroute`) with two enabled transitions, so the expected file
  for `i2-bitemporal` is a two-element trace set and every substrate check is
  inclusion, not equality (§20).

The bitemporal snapshot is not a primitive here. `r0lang.tau_rules` generates
`Retracted_R` and `R` as ordinary stratified rules over `Hist_R`, exactly as
§7 defines them. Both evaluators, the transparent substrate and the
reflection check treat them like any other rule, which is the concrete form of
the paper's remark that τ factors into S, D, χ and F (§22).

### The two gates

**Answer key.** `gen_expected.py` runs the reference evaluator over every
permitted successor, and recomputes every derived state it visits with the
SQLite oracle. The two share a spec loader and nothing else: one is a binding
walk written from the paper, the other is SQL executed by SQLite. Disagreement
aborts generation. A substrate passes the gate when every trace it produces is
inside the expected set.

**Reflection.** `reflection_check.py` extracts the source constructor graph
G_R from the spec (`r0lang.constructor_graph`) and the call graph of the
artifact from its Python AST, and checks the six conditions of §13:

1. constructor preservation — every G_R node has a function of its kind
2. dependency preservation — every source edge is a call edge
3. addressability — every node has an image
4. local adequacy — *delegated to the answer key*, by design
5. injectivity — distinct nodes, distinct functions
6. bounded locality — no public function that is not an image; no call
   between images that is not a source edge; no run-time name resolution

When 2 and 6 hold, the call graph restricted to images is isomorphic to G_R:
the source structure is recoverable from the artifact. For the transparent
substrate that is 88 nodes to 88 functions and 117 edges to 117 calls.

The naming convention is the map φ and is the only contract a substrate must
honour to be checkable: `c_pred_P`, `c_rule_id`, `c_mu_<preds>`, `c_t_Name`,
`c_constraint_P`, `c_obs_name`.

### The three substrates

*transparent* — `transpile.py` emits a rule body as explicit nested loops, a
non-recursive predicate as the union of its rules, and a recursive stratum as
a `c_mu_*` driver that iterates its rules to a fixed point. The executor
(`runtime.py`) never reads the spec JSON; every domain question is a call into
the module.

*tangled* — the transparent module with every predicate read inside a rule
routed through `_dispatch(name, S)`, which resolves the target by name. Same
computation, same answers. Condition 2 fails because the dependencies are now
strings, and condition 6 fails because a helper resolves callees at run time.
This is the small-scale shape of the dependency-flooding obstacle in §23.

*interpreter* — the rulebook loaded as inert JSON and handed to one universal
evaluator (the SQLite oracle, compiling at request time). Zero image functions.
Conditions 1, 2, 3 and 6 fail. Note what makes this an interpreter is not
SQL: a substrate that *materialised* the same SQL as one named view per rule
would pass reflection. What fails is that nothing is materialised.

### Tests

`tests/` runs the pipeline from scratch (the transparent and tangled modules
are regenerated into a temp dir) and asserts, among other things:

- `r0-lint` accepts the spec and rejects value generation, unstratifiable
  negation, unstratifiable aggregation, a range-restriction violation and a
  non-monotone history;
- reference and oracle agree on every visited state (44 of them) and produce
  identical trace sets; the committed expected files are current;
- the nondeterministic command yields exactly two observably different traces;
  rejected transitions leave the state unchanged; empty groups behave as §5
  says; a retraction recomputes the recursive closure; the correction is
  visible by valid time and by knowledge time and never destroys history;
- the transparent substrate passes both gates and, with all successors
  explored, reproduces the entire permitted set;
- both controls pass the answer key and fail reflection on the expected
  conditions;
- the reflection check catches a *single* hidden dependency and a *single*
  added one (two mutation tests).

## What this does not show

- **Assumption DC.** The answer key tests that this Python and this SQLite
  compute the denotations §2 and §5 stipulate. That is the adequacy obligation
  of §11, not the theorem, and it is only tested on these inputs.
- **The existing demos are not assessed.** `r0-lint` reads the R0 JSON format
  in `r0/`, not `effortless-rulebook.json`. A converter from the Airtable-shaped
  rulebook to R0 is the natural next step, and it is where the question "which
  existing demos are in R0?" gets its first real answer. Expect most to fall
  outside R0 as stated, usually on nulls or on serial-only semantics; that is
  data, not a problem.
- **One external oracle.** SQLite is independent of the reference evaluator's
  mechanism but the SQL compiler is ours. A third oracle through an off-the-shelf
  Datalog engine (Soufflé) would remove that dependency.
- **Replication.** Nothing here is peer-reviewed. It is arranged so that
  someone else can clone it, run one command, and diff.

## Adding a substrate

Emit an artifact in which each G_R node has exactly one function named by the
convention above, calls between those functions are exactly the source edges,
and nothing resolves callees by name. Register it in `conformance/run.py` with
a `run(inputs)` that returns `{"traces": [...]}` in the engine's format. Both
gates will then run on it.

## Local transpiler bus (`127.0.0.1:4242`)

> **All 11 local transpilers are hosted by the effortless CLI itself.** Start
> the bus with `effortless serve -port 4242` from the repo root; it serves every
> tool under `effortless-tools/<name>/` — `oss-postgres-calculated-to-rulebook`,
> `oss-rulebook-to-python`, `oss-rulebook-to-golang`, `oss-rulebook-to-cobol`,
> `oss-rulebook-to-owl`, and more — as a first-class route any `effortless
> build` can call. `GET /` lists them.
>
> **Address it as `127.0.0.1`, never `localhost`.** The host binds the literal
> prefix `http://127.0.0.1:<port>/`, so a request carrying a `localhost` Host
> header gets a bare 404 with no explanation.
>
> **Every repo-local route carries the `oss-` prefix.** The bare names
> (`rulebook-to-python`, `rulebook-to-xlsx`, `rulebook-to-owl`,
> `rulebook-to-airtable`, `airtable-to-rulebook`) belong to the commercial
> catalog as `effortless/effortless/<tool>`; the prefix is the only thing
> keeping a repo-local route from shadowing one.
> `orchestration/local_tool_shim.py` refuses to run if any tool is missing it.
